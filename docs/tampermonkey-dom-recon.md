# Tampermonkey DOM Reconnaissance for Guardian Bridge

**Task**: Review the legacy `Enhanced Grok Export v2.4` script to extract DOM selectors and heuristics for the future Guardian Browser Bridge.

## 1. Useful Selectors and Heuristics Extracted
Based on the export script, Grok's web UI relies heavily on modern Tailwind CSS classes as of early 2025. 
- **Message Containers**: `.message-bubble` (Primary), `.response-content-markdown`, or legacy `div[class*="css-146c3p1"]`.
- **Human Identifier**: Elements containing the Tailwind class `bg-surface-l1`.
- **Grok Identifier**: Elements containing `max-w-none` but missing `bg-surface-l1`.

## 2. Reusable Parts for the Guardian Bridge
- **Finding the latest user-authored message**:
  We can use `document.querySelectorAll('.message-bubble')` and filter for elements containing `bg-surface-l1`. The last element in that filtered array represents the latest user message in the DOM.
- **Distinguishing User vs. Grok**:
  The `bg-surface-l1` vs `max-w-none` heuristic is highly efficient. We do *not* need the complex regex/length analysis (`detectGrokSpeakerAdvanced`) used in the export script, as we only care about tracking the visual state of the chat thread.
- **Detecting when Grok has finished responding (Postflight Capture)**:
  The export script relies on timeouts and scroll heights. For the Guardian bridge, we will need to upgrade this to a `MutationObserver` watching the last Grok bubble (`.message-bubble` without `bg-surface-l1`) to see when the streaming text stops or when the "Stop generating" UI element disappears.
- **Adding a Guardian UI status/banner**:
  The export script successfully injects custom UI using absolute/fixed positioned `div` elements appended directly to `document.body` with high z-indexes (e.g., `z-index: 10000`). We can reuse this exact styling approach to display the "Guardian Blocked" or "Preflighting..." overlays without breaking Grok's underlying React layout.

## 3. Missing Elements (Required for the Bridge)
Because the export script only *reads* data and never intercepts or modifies user input, the most critical pieces for the Bridge are missing:
- **Textarea Selector**: We need the specific selector for the chat input box (e.g., `textarea[placeholder="Ask Grok"]`, `textarea`, or `[data-testid="message-input"]`).
- **Send Button Selector**: We need the selector for the submit action (e.g., `button[aria-label="Send"]` or `svg path`).
- **Submit / Enter Interception Strategy**: Grok uses React. To stop the prompt from sending before the Guardian preflight finishes, we must hijack the `Enter` `keydown` event and the Send Button `click`/`mousedown` event at the `window` capture phase using `e.stopPropagation()` and `e.preventDefault()`.
- **React State Update Strategy**: To inject the Guardian report on `proceed`, we cannot simply do `textarea.value = text`. React's virtual DOM will ignore it. We must use a native setter bypass:
  ```javascript
  const nativeSetter = Object.getOwnPropertyDescriptor(window.HTMLTextAreaElement.prototype, 'value').set;
  nativeSetter.call(textarea, enrichedPrompt);
  textarea.dispatchEvent(new Event('input', { bubbles: true }));
  ```

## 4. Next Discovery Steps & Risks
**Risks:**
- **Tailwind Class Churn**: Classes like `bg-surface-l1` are generated by Tailwind and could change if Grok updates its UI theme.
- **React Event Bubbling**: Successfully preventing default on a React `onClick` event from a Vanilla JS Tampermonkey script is notoriously difficult. 

**Next Steps for Implementation:**
1. Manually inspect the Grok web UI to find stable `data-testid` or `aria-label` attributes for the `textarea` and Send button.
2. Write a minimal Proof-of-Concept Tampermonkey script that *only* attempts to intercept the Send action and `console.log` the text without sending it.
3. Once the interception and React-bypass injection are proven stable, hook up the actual `fetch()` call to `POST /preflight`.
