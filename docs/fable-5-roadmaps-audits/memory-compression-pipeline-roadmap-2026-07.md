## 1. Measured findings first — the problem is not what it looks like

I measured the corpus before designing. Three discoveries reframe the request:

### 1.1 `event-log.md` is not bloated — it is *monolithic*

The file is currently only **5.1 KB / 2 session entries**, because a manual rotation habit already exists: `scarlett-full-detailed-chronological-summary-4/5/6.md` are **rotated event logs** — same `# Event Log` header, same entry format (~15 KB each). The chain `event-log → chronological-summary-N → summarisation/` is your compression pipeline; it's just manual, unscheduled, and format-broken.

The real defect: **entries are delimited by `**Session/Date:**` bold text, not headings.** `splitMarkdownSections` (`src/markdown.ts`) splits only on `#`-headings, and these files have exactly one `#` at line 1. Consequences, all verified:

- `event-log.md` indexes as **one single chunk**. So does each 15 KB chronological-summary file.
- One embedding averages over every event in the file → the vector goes mushy as the log grows. This is the *actual* mechanism behind "bloat degrades retrieval quality," and it is already active at 15 KB — my report audit found the chunk topic "Event Log — Scarlett & Benjamin Narrative" appearing as a top-2 precedent **65 times**, matching everything because it contains everything.
- **Truncation bias toward the oldest events:** Guardian passes `max_chars_per_result: 2500–3000`. A 15 KB monolithic chunk gets cut at ~20% — from the *top*. Retrieval therefore returns the file's **oldest** entries and silently discards the newest. In an append-only log, this is precisely backwards.

### 1.2 Incremental reindex cost is O(file), not O(delta)

`reindexSingleFile` (`src/reindexer.ts`) re-uploads **every section of the file** on each write: sequential uploads, a 5 s propagation wait, then sequential attach with up to 8 retry polls per section. Today event-log reindex is cheap only because the file is one chunk. Fix the chunking (1.1) and let the file grow to 50 sessions, and every single beat-advance append from the Guardian write-back pipeline (Pillar C of the previous roadmap) would cost 50 uploads + 50 attaches. **Hot files must stay small — rotation is not optional once Pillar C ships.**

### 1.3 The fidelity standard is already written down

`summarisation/docs/fidelity_vs_token_cost_postmortem.md` documents the last manual compression campaign: summary_1 over-delivered (7-subsection essays per scene, 4–8× token blowup), later summaries drifted shallow under token pressure, and nobody decided either. It also states the operator's actual goal verbatim: **blow-by-blow chronology + emotional texture + enough context that retrieval "gives you the lived experience back."** The converged output format exists and is already indexed and retrieving well: `summarisation/*/narrative_records/chunk_N_narrative_emotional_record.md` (`## 1. Chronological Blow-by-Blow` / `## 2. Durable Canon & Character Updates` / `### Relational Milestones` / `## 3. Current-Canon Compatibility Warnings`).

Also load-bearing: **`emotional-milestones.md` already exists as the emotional-resonance ledger**, and event-log entries already cross-reference it ("Rich emotional detail of the transition conversation is recorded in emotional-milestones.md"). The pipeline should formalize this file as *protected, never-compressed*, and make milestone extraction a mandatory pre-compression step — that is the structural answer to "don't strip the delicate resonance."

## 2. Target architecture: a memory temperature model

```text
HOT      project_source_files/event-log.md
         Last ~6–8 sessions, full entry detail, one ## heading per session.
         Written by Guardian beat-advances (Pillar C). Small forever, by rotation.

WARM     project_source_files/arc-chronicles/arc-NN-<slug>.md
         Rotated event-log entries, VERBATIM (no LLM, no loss), grouped by arc.
         Replaces the ad-hoc chronological-summary-N pattern.

COLD     project_source_files/historical/arc-NN-<slug>/
         narrative-record.md + durable-canon.md, generated by LLM compression
         when an arc closes. Follows the proven narrative_records format.

PROTECTED (never compressed, never rotated):
         emotional-milestones.md, current-state.md, master-context.md,
         story-bible.md, memory-protocol.md, character bibles.

WORKSHOP (not indexed): summarisation/ — raw exports, prompts, past campaign
         artifacts. Existing narrative_records stay indexed where they are.
```

Rules that make it safe:

1. **Rotation ≠ compression.** Rotation is a deterministic verbatim move (no LLM, no fidelity loss, reversible) and can run autonomously. Compression involves an LLM and runs only at arc boundaries, gated and staged for review.
2. **Exactly one indexed copy per event at each fidelity level.** When an arc is compressed COLD, its WARM chronicle leaves the index (moved to `summarisation/compressed/` as workshop backup) — otherwise retrieval returns near-duplicate hits from both layers.
3. **Milestones flow up, never down.** Before any compression, relationship milestones/firsts are extracted into `emotional-milestones.md`. A "first" never exists solely in a compressible layer.

Answering the three questions directly:

- **When to compress?** Rotate on a size trigger (hot log > 8 sessions or > 12 KB), checked after every Guardian write. Compress on an *arc trigger* — the `scene_transition` field the Pillar C auditor already emits, plus an explicit operator command — never on a timer alone.
- **How to preserve resonance?** Milestone pre-extraction to the protected ledger + the narrative-record format (which is chronology *with* feeling, per the postmortem) + a deterministic fidelity gate (§4.3) + human approval through the existing staging pipeline.
- **How does it interact with indexing?** Rotation shrinks the hot file so the O(file) reindex stays cheap; every pipeline write goes through the existing `performApprovedStoryUpdate` → background `reindexSingleFile` path (never bypassing it); new files get source-priority profiles so temperature maps to rank boost.

## 3. P0 — Fix the chunking, automate rotation (no LLM, ships this week)

### 3.1 Reformat episodic files to heading-per-session — the single highest-ROI item

**Files:** `project_source_files/event-log.md`, `scarlett-full-detailed-chronological-summary-4/5/6.md` (one-time edit), then reindex each.

Convert every `**Session/Date:** X` delimiter to a heading:

```markdown
## Session — Friday, Mid/Late October 2026 — Eifel drive → Nürburgring track day (out lap)
```

Effect: the chunker splits per session; each session gets its own embedding, its own `section` label, its own `section_index`; truncation bias disappears; `expand_context_around_chunk` (being re-enabled by the retrieval P0 work) can walk to adjacent sessions — that is exactly what neighbor-expansion was built for. Zero code changes; the indexer already does everything right once the headings exist.

Also update the format template at the top of `event-log.md` and `docs/memory-maintenance-guide.md` §Layer 3 to mandate the heading form.

### 3.2 Align the Guardian write path with the new format

**File:** `scarlett-guardian-mcp/src/guardian/memory-writeback.ts` — beat-advance appends to `event-log.md` must emit `## Session — <story-date> — <short label>` headers (coordinate with Grok 4.5's in-flight Pillar C work; this is one formatting function).

### 3.3 New RAG tool: `rotate_event_log` (deterministic, atomic, autonomous-safe)

**File:** `rag-memory-mcp/src/server.ts` (new tool) + NEW `src/rotation.ts`.

```ts
// src/rotation.ts
export interface RotationPlan {
  retainedSessions: string[];    // last N session headings kept in hot log
  rotatedSessions: string[];     // headings moved out, verbatim
  targetChronicle: string;       // project_source_files/arc-chronicles/arc-NN-<slug>.md
}
export function planRotation(eventLogMarkdown: string, retainCount: number, arcSlug: string): RotationPlan;
export async function executeRotation(plan: RotationPlan, dryRun: boolean): Promise<RotationResult>;
```

- Parses sessions by the `## Session —` headings from 3.1 (fallback: `**Session/Date:**` + `---` delimiters during migration).
- Transaction under the existing `writeMutex`: (a) append rotated sessions **verbatim** to the target chronicle (creating it with a proper `#` title + arc metadata header if absent); (b) rewrite the hot log with header template + retained sessions; (c) fire background `reindexSingleFile` for **both** files, sequentially (the reindexer is already mutex-safe and attach-first).
- File backups via the existing backup path in `performApprovedStoryUpdate` — route both writes through it rather than raw `fs`, so backup/mutex/validation come free.
- Tool schema: `{ retain_sessions?: number = 6, arc_slug?: string, dry_run?: boolean }`. Dry-run returns the plan (which sessions move where) without writing.
- Because rotation is verbatim and reversible, it is safe to run **autonomously without human review** — this is the deliberate contrast with compression.

**Arc slug source:** default to a slug of the current arc from `current-state.md`'s `Last Updated` line (e.g. `arc-09-germany-trip`); overridable by the caller. Maintain a tiny `arc-chronicles/ARC_INDEX.md` (append a line per rotation: arc slug, date range, session count) so humans and the compression step can find arc boundaries later.

### 3.4 Auto-trigger after Guardian writes

**File:** `rag-memory-mcp/src/server.ts`, inside the write path *after* a successful `update_story_state`/`approve_staged_story_update` targeting `event-log.md`: count `## Session —` headings; if > `ROTATION_RETAIN + ROTATION_HYSTERESIS` (default 6 + 2), schedule `rotate_event_log` on the same background queue as the reindex (rotate first, then the rotation's own reindexes subsume the pending one). Config via env: `EVENT_LOG_RETAIN_SESSIONS=6`, `EVENT_LOG_ROTATE_MAX_CHARS=12000` (whichever trips first).

Report the rotation in the tool's JSON response (`rotation: { triggered: true, rotated: 3, chronicle: "…" }`) so Guardian's `memory_write` observability (Pillar C) captures it.

### 3.5 New source-priority profiles

**File:** `rag-memory-mcp/src/source-priority.ts`:

- `arc-chronicles/` path rule → new role `arc_chronicle`, priority 75, rankBoost 0.03 (between `event_log` 80 and `story_bible` 70 — recent-but-not-live).
- `historical/arc-*/` path rule → `historical_narrative`, priority 60 (matches the existing narrative_records treatment).
- Add both roles to the `source_roles` enum in the two search-tool schemas in `server.ts`.

## 4. P1 — Arc compression with fidelity gates (LLM, staged, human-approved)

### 4.1 Trigger: arcs close, timers don't

Compression runs when an **arc closes**, detected by either:

- the Pillar C auditor's `scene_transition` field with a location/time jump that matches the end of the chronicle's arc (Guardian marks the chronicle "closeable" in `ARC_INDEX.md`), or
- an explicit operator command (OOC or CLI) — always available, always wins.

Rationale: compressing a *live* arc guarantees rework and risks contradicting `current-state.md`. Closed arcs are stable input. Expected cadence: every 1–3 weeks of play — low volume, so this can afford care.

### 4.2 The pipeline: NEW `rag-memory-mcp/scripts/compress-arc.ts` (CLI first, MCP tool later)

```text
compress-arc --chronicle project_source_files/arc-chronicles/arc-09-germany-trip.md [--dry-run]

 Step 1  MILESTONE EXTRACTION (protects resonance before anything is condensed)
         LLM pass over the chronicle: extract relationship milestones, firsts,
         emotional turning points → staged APPEND to emotional-milestones.md
         (matching its existing "## <date> — <place> (<context>)" format).
         Rule: anything matching "first X", explicit declarations, boundary/consent
         evolutions, or identity-related reveals MUST be extracted.

 Step 2  NARRATIVE RECORD (the cold artifact)
         One LLM call (gpt-5.6-terra, reasoning MEDIUM — this writes lore; never low),
         output in the PROVEN narrative_records schema:
           # Narrative & Emotional Record: arc-09-germany-trip
           ## 1. Chronological Blow-by-Blow      (### per scene/beat, prose WITH feeling)
           ## 2. Durable Canon & Character Updates
           ### Facts & World-building / ### Scarlett / ### Benjamin / ### Relational Milestones
           ## 3. Current-Canon Compatibility Warnings
         Prompt encodes the postmortem's calibration explicitly:
         "Blow-by-blow narrative with emotional texture. NOT a 7-subsection analysis
          per scene; NOT clinical bullets. Target 3–5:1 condensation. Preserve verbatim
          any quoted dialogue, Swedish phrases, and named sensory details present in
          the source." (This is the guardrail both past failure modes — summary_1
          bloat and later-summary shallowness — lacked.)

 Step 3  FIDELITY GATE (deterministic — see 4.3). Fail → keep staged, flag for human.

 Step 4  STAGE both artifacts via the existing stage_story_update tool:
           project_source_files/historical/arc-09-germany-trip/narrative-record.md
           emotional-milestones.md (append)
         Human reviews/approves via the review-staged CLI (Pillar C item 10);
         approval triggers background reindex automatically.

 Step 5  POST-APPROVAL housekeeping (part of the script, --finalize):
         move the WARM chronicle to summarisation/compressed/ (workshop backup,
         leaves the index), remove its manifest entries via reindex-after-delete,
         update ARC_INDEX.md status → compressed.
```

Write-path note: everything targets `project_source_files/**` — inside `validateWritableSourceFile`'s allowlist — so the pipeline needs **zero new write primitives**; it composes the staging, approval, backup, mutex, and background-reindex machinery that already exists (and that Pillar C is putting into production use).

### 4.3 The fidelity gate — `src/compression-gate.ts` (deterministic, no LLM)

Modeled on Pillar C's `validateStateRewrite`; a compression is rejected when any check fails:

1. **Schema:** all required headings present, in order.
2. **Compression ratio bounds:** output between 15% and 45% of source chars. Below → over-compressed (shallowness drift); above → essay bloat (summary_1 failure). Both historical failure modes get a tripwire.
3. **Entity preservation:** every capitalized proper noun + every date/day token in the source appears in the output *or* in an explicit `### Omitted` list the generator must emit. No silent disappearance of people, places, or when.
4. **Milestone cross-check:** every `### Relational Milestones` bullet in the record has a counterpart staged into `emotional-milestones.md` (Step 1 output) — the ledger and the lore may not diverge.
5. **Quote preservation:** lines the extractor flagged as verbatim-protected (dialogue in quotes, Swedish phrases) appear character-exact in the output.
6. **No RAG meta / tool dialect** (reuse `isRagMetaText`).

### 4.4 Backfill the existing monoliths

Run the same pipeline over `scarlett-full-detailed-chronological-summary-4/5/6.md` (they are closed-arc warm chronicles in all but name), **one file at a time, human-approved each**. After 3.1's reformat they retrieve acceptably, so this is quality improvement, not firefighting — schedule it after the pipeline has proven itself on the first naturally-closing arc (the Germany trip, imminent).

## 5. P2 — Lifecycle automation and retrieval integration

1. **Scheduled compaction check:** a weekly job (cron or Cursor Automation) runs `rotate_event_log --dry-run` + lists closeable arcs; notifies rather than acts. Autonomy stays at rotation; compression keeps its human gate until §7's criteria are met.
2. **`story_epoch` stamping** (shared item with the recency roadmap's Layer 2): the arc number from `ARC_INDEX.md` *is* the epoch. Stamp `story_epoch` + `is_live_state` attributes at index time; batch with the store/manifest reconciliation reindex. Cold records then carry their place in story-time as first-class metadata, and Guardian's recency demotion extends beyond same-day supersession.
3. **Cross-layer dedup guard in the retriever:** when results include both an `arc_chronicle` and a `historical_narrative` chunk covering the same arc (match on arc slug in path), keep the higher-fidelity one for the query type — chronicle for precedent detail, record for arc overview. Cheap path-based check in `retriever.ts` result post-processing.
4. **Scorecard extensions** (audit script): per-file section-count and max-chunk-size histograms (alert > 4 KB/chunk), hot-log session count, days-since-last-rotation, arcs pending compression, dedup-hit rate. The monolith problem in §1.1 went unnoticed for weeks precisely because nothing measured chunk sizes.
5. **Compression of `summarisation/` legacy tiers** (optional, last): summary_2's `archive_pre_reprocessing` and other workshop-only material can graduate through the same pipeline if retrieval gaps for early-era lore are ever observed. Don't do it speculatively.

## 7. Acceptance criteria

- **Chunking:** no indexed chunk from an episodic file exceeds ~4 KB; `event-log.md` never exceeds retain+hysteresis sessions after any write; truncation-bias case (newest event missing from retrieval of event-log) no longer reproducible.
- **Reindex cost:** event-log reindex after a beat append uploads ≤ retain+1 sections, measured in reindexer logs.
- **Rotation:** verbatim invariant holds — `cat hot-log rotated-entries` reconstructs the pre-rotation file byte-identically (modulo the header template); demonstrated in the rotation test.
- **Compression fidelity:** first arc record passes all six gate checks *and* human review without edits before auto-staging is trusted; ratio lands in the 15–45% band; every milestone in the record exists in `emotional-milestones.md`.
- **No dedup regressions:** after finalizing an arc, retrieval for that arc's events returns the cold record (and hot/protected files) but not the retired chronicle.
- **Resonance spot-check (the human one):** the operator re-reads one compressed arc's narrative record and confirms it "gives the lived experience back" — the postmortem's own success criterion, and the only one that ultimately matters.

---

## 8. Closing note

The corpus already contains every ingredient of this pipeline: a rotation habit (the chronological-summary files), a proven cold-storage format (narrative records), a protected resonance ledger (`emotional-milestones.md`), a documented fidelity calibration (the postmortem), and — after Pillar C — a staging/approval/reindex machine for safe writes. What's missing is not invention but **plumbing and gates**: headings so the chunker can see sessions, a deterministic rotation so the hot file stays hot, an arc-boundary trigger so compression happens at natural joints, and a fidelity gate encoding the lessons both past failure modes taught. The one non-negotiable design line: **rotation is autonomous because it loses nothing; compression is gated because it can.**
